# 규모 측정

측정일 2026-10-27(Phase 5 완료 시점). 원본 수치는 [benchmark.json](benchmark.json), 측정 도구는 [tools/benchmark.py](../tools/benchmark.py)다.

- 환경: Windows 11, Intel i7-12700(12코어 20스레드), RAM 15.7GB, Python 3.12.9, SQLite 3.45.3
- 데이터:
  - 일반 `ingest` 경로로 만든 합성 페이지(한국어·영어 단어, 오류 코드, 관계, 용어 포함)
  - Phase 5 묶음 소속 규칙에 따라 500페이지마다 최상위 목차 1개와 하위 목차 10개(각 50페이지)를 함께 만든다(10,000페이지에서 목차 220개).
- 방법: 항목마다 30회 실행. 원격 조사(agy) 시간은 포함하지 않는다. HTTP 항목은 로컬 서버까지의 왕복이다.
- 목표(spec §13): 1,000페이지에서 조회 p95 1초 이내, 그래프 응답 p95 0.5초 이내

## 측정 중 고친 문제

- Phase 4: 처음 측정에서 10,000페이지 생성이 259초 걸렸다.
  - 원인: 저장할 때마다 검색 색인 행을 색인되지 않은 `page_id` 열로 찾아 지워서, 페이지 수에 비례하는 스캔이 저장마다 일어났다(전체로는 제곱 비례).
  - 수정: 색인 행이 페이지와 같은 rowid를 쓰도록 바꿨다(스키마 7, 업그레이드 시 색인 한 번 재생성). 10,000페이지 생성이 19.2초가 됐다.
- Phase 5: 10,000페이지에서 세션 목록이 p95 4,552ms였다. 원인은 두 가지였다.
  - 목차 구성원 표에는 하위 문서 쪽 인덱스가 없는데, "목차에 없는 문서"를 페이지마다 하위 문서 조건으로 찾았다. 저장 시 소속 검사도 같은 방식이었다.
  - 묶음마다 소스 수를 셀 때 저장소 전체의 소스–문서 연결을 만든 뒤 걸렀다. 통계가 없는 SQLite가 근거 표 전체에서 출발하는 순서를 골랐다.
  - 수정: 집합 비교(`NOT IN`, 묶음 단위 조회)로 바꾸고, 문서 쪽 표부터 읽도록 조인 순서를 고정했다. 스키마는 바꾸지 않았다. 같은 조건의 빠른 측정에서 세션 목록이 약 130ms, 본 측정 p95는 141.6ms다.
- Phase 5: 브라우저가 페이지를 다시 열 때 끊긴 요청이 서버 오류(`ConnectionAbortedError`)로 기록됐다. 오류가 아니므로 기록하지 않는다.

## 읽는 법

- 이 측정은 같은 PC에서 Phase 4 측정보다 바꾸지 않은 항목도 전반적으로 느리게 나왔다(예: 읽기 10,000페이지 5.0 → 13.5ms). PC 부하에 따른 차이이며, 항목 사이 비교는 같은 측정 안에서 한다. 목표 두 가지는 모두 안쪽이다(1,000페이지 조회 161ms, 그래프 HTTP 58ms).
- 브라우저 준비 시간은 탭을 열고 데이터를 받아 그래프를 다 그릴 때까지다.
  - 전체 그래프는 표시 한도(150)에서 멈추므로 10,000페이지에서도 그리는 양은 같다.
  - 대부분은 노드 배치(force layout) 계산이다. 같은 탭에서 다시 그릴 때는 계산한 배치를 재사용한다.
- 3자 미만 검색어("설치", "캐시")는 trigram 색인을 쓸 수 없어 본문을 부분 문자열로 훑는다. 그 비용만 따로 잰 값이 "본문 스캔만"이고, 조회 수치에는 이미 들어 있다.
- 저장소 생성 시간에는 Phase 5의 소속 검사가 포함된다.
