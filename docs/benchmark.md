# 규모 측정

측정일 2026-10-27. 원본 수치는 [benchmark.json](benchmark.json), 측정 도구는 [tools/benchmark.py](../tools/benchmark.py)다.

- 환경: Windows 11, Intel i7-12700(12코어 20스레드), RAM 15.7GB, Python 3.12.9, SQLite 3.45.3
- 데이터: 일반 `ingest` 경로로 만든 합성 페이지(한국어·영어 단어, 오류 코드, 관계, 용어 포함)
- 방법: 항목마다 30회 실행. 원격 조사(agy) 시간은 포함하지 않는다.
- 목표(spec §13): 1,000페이지에서 조회 p95 1초 이내, 그래프 응답 p95 0.5초 이내

| 항목 (p95, ms) | 100 | 1,000 | 10,000 |
| --- | ---: | ---: | ---: |
| 조회 `query` (Markdown 생성 포함) | 19.5 | 106.1 | 250.9 |
| 읽기 + Markdown 렌더 | 3.5 | 3.6 | 5.0 |
| 관계 `neighbors` | 3.4 | 3.4 | 4.9 |
| 그래프 데이터(기본 150/300) | 7.8 | 19.4 | 54.3 |

| 브라우저 검토 화면 준비(Chromium) | 365.7 | 692.0 | 1006.8 |
| 저장소 생성 시간(초) | 0.2 | 1.1 | 19.2 |

## 측정 중 고친 문제

처음 측정에서 10,000페이지 생성이 259초 걸렸다. 저장할 때마다 검색 색인 행을 색인되지 않은 `page_id` 열로 찾아 지워서, 페이지 수에 비례하는 스캔이 저장마다 일어났다(전체로는 제곱 비례). 색인 행이 페이지와 같은 rowid를 쓰도록 바꾸고(스키마 7, 업그레이드 시 색인 한 번 재생성), 10,000페이지 생성이 19.2초가 됐다. 4,000페이지 저장소에 한 건 저장은 0.06초다.

## 읽는 법

- 브라우저 화면 준비 시간은 페이지를 열고 그래프를 다 그릴 때까지다. 노드 수는 기본 상한(150)에서 멈추므로 10,000페이지에서도 그리는 양은 같다.
- 3자 미만 검색어("설치", "캐시")는 trigram 색인을 쓸 수 없어 본문을 부분 문자열로 훑는다. 그 비용만 따로 잰 값이 "본문 스캔만"이고, 조회 수치에는 이미 들어 있다.
